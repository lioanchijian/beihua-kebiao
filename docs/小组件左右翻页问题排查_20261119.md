# 桌面小组件结构梳理与左右翻页失效排查

日期：2026-11-19
状态：已修复，并在真机（vivo V2362A / Android）完成点击验证
涉及版本：1.0.9.13 及之前、1.0.9.15、1.0.9.16

---

## 一、小组件整体结构

### 1. 两种小组件

| 类型 | 实现类 | 布局 | 数据方式 |
|---|---|---|---|
| 周课表 | `widget/ScheduleWidget.kt` | `res/layout/widget_schedule.xml` + `widget_schedule_row*.xml` | `RemoteViewsService` + `ListView`，12 节 × 7 天 |
| 今日课表 | `widget/ScheduleDayWidget.kt` | `res/layout/widget_schedule_day.xml` | 静态 `RemoteViews` 卡片，最多 6 组卡 |

### 2. Provider 与兼容壳

Manifest 里实际注册的只有旧包名兼容壳：

- `com.buct.course/com.tyust.course.widget.ScheduleWidget`
- `com.buct.course/com.tyust.course.widget.ScheduleDayWidget`

对应类：

- `com/tyust/course/widget/LegacyWidgetProviders.kt`
  - `class ScheduleWidget : com.buct.course.widget.ScheduleWidget()`
  - `class ScheduleDayWidget : com.buct.course.widget.ScheduleDayWidget()`

真正的逻辑在：

- `com/buct/course/widget/ScheduleWidget.kt`
- `com/buct/course/widget/ScheduleDayWidget.kt`

`WidgetProviders` 负责同时认识新旧两套组件名：

- `week()`：新 `com.buct.course.widget.ScheduleWidget` + 旧 `com.tyust.course.widget.ScheduleWidget`
- `day()`：新 + 旧
- `idsFor()` / `weekIds()` / `dayIds()`：合并两边已添加的实例
- `refreshAll()`：向新旧两边广播 `REFRESH_WIDGET`

### 3. 实例配置

`widget/WidgetConfigStore.kt` 按 `appWidgetId` 存：

- `title_<id>`：实例标题；空则回落到全局标题/朋友课表名/兜底
- `account_<id>`：该实例显示哪个本机账号
- `source_<id>`：空 = 本机账号；`friend:<id>` = 某位朋友的课表

配置入口：

- 设置页「小组件管理」：`ui/screen/WidgetSettingsScreen.kt`
- 桌面点击小组件标题：`ui/widget/WidgetConfigActivity.kt`
- 首次添加不声明 `android:configure`，避免部分 ROM 添加失败；改为点击标题进配置

### 4. 字号与主题

- `widget/WidgetTextSizes.kt`：RemoteViews 不能改样式表，按 id 显式 `setTextSize`；周/日两套布局各自维护基准字号。
- 主题：读 `appearance_settings` 的 `theme_mode`，再结合系统深色模式决定文字/背景色。
- 字体缩放：读 `ScheduleSettingsManager.widgetFontScale`。

## 二、周课表翻页链路（正常设计）

1. `updateAppWidget()` 构建 `RemoteViews`，给 `widget_prev_week` / `widget_next_week` 绑定 `PendingIntent.getBroadcast`。
2. 点击箭头 → 广播 `ACTION_PREV_WEEK` / `ACTION_NEXT_WEEK`。
3. `ScheduleWidget.onReceive()`：
   - 读全局 `widget_prefs.current_week`
   - 前翻 `-1`，下限 1；后翻 `+1`
   - 写入 `current_week` 和 `last_week_nav`
   - 用 `partiallyUpdateAppWidget` 更新 `widget_week_info` 和 7 个星期表头
   - 用 `notifyAppWidgetViewDataChanged(ids, R.id.widget_list)` 让列表重读周数
4. `ScheduleWidgetService` 的 `onDataSetChanged()`：
   - 同样读 `widget_prefs.current_week`
   - 24 小时内手动翻过周则保留，否则回到今天所在周
   - 按 `ScheduleWeeks.visibleIn(currentWeek)` 过滤课程
   - `rowHasCourse` 先判断该节是否有课，空行走快速路径
   - `getViewAt()` 按单节/首节/末节选择不同 row 布局
5. 数据来源：
   - 优先 `WidgetScheduleSource.loadFriendJson(context, appWidgetId)`
   - 否则读实例账号 / 当前账号的本机课表缓存

注意：`current_week` 是**全局** prefs，不是按实例隔离；多个周课表会一起翻页。这是设计现状，不是本次“完全不能翻”的直接原因。

## 三、今日课表翻页链路

1. `buildViews()` 给 `widget_prev_day`、`widget_next_day`、`widget_back_today` 绑定广播 PendingIntent。
2. `ScheduleDayWidget.onReceive()`：
   - 读 `day_widget_prefs.day_offset`
   - 前翻 `-1`、后翻 `+1`、回到今天 `0`
   - 写入 offset
   - 用 `WidgetProviders.dayIds()` 取全部今日课表实例
   - 对每个实例 `buildViews()` 后 `partiallyUpdateAppWidget`
3. `ScheduleDayRemoteViewsFactory` 构建当天课程/考试卡片，最多 6 张。
4. 日期栏显示 `月日 · 星期 · 第几周`；非今天时按钮显示「回到今天」。

今日课表的箭头和「回到今天」也使用同一个模式，因此本次问题同样会影响它。

## 四、1.0.9.13 与当前版本的差异

### 1.0.9.13 / 1.0.9.14

- 周组件类：`com.tyust.course.widget.ScheduleWidget`
- Manifest：`android:name=".widget.ScheduleWidget"`，包名也是 `com.tyust.course`，所以解析后是同一个类
- 箭头 PendingIntent：`Intent(context, ScheduleWidget::class.java)`，目标就是这个已注册类
- 结果：广播能到 `onReceive`，翻页正常

### 1.0.9.15 包名迁移

关键提交：`257f1e7`（release: 1.0.9.15）

做了两件事：

1. 逻辑类整体搬到 `com.buct.course.widget.ScheduleWidget` / `ScheduleDayWidget`
2. Manifest 为了保住老桌面实例，把 provider 改成旧包名兼容壳：
   - `com.tyust.course.widget.ScheduleWidget`
   - `com.tyust.course.widget.ScheduleDayWidget`

但箭头代码仍然是：

```kotlin
val prevIntent = Intent(context, ScheduleWidget::class.java).apply {
    action = ACTION_PREV_WEEK
}
```

此时 `ScheduleWidget::class.java` 已经是 **新包名类** `com.buct.course.widget.ScheduleWidget`。

Manifest 里没有注册这个新类，只有旧包名兼容壳。于是：

- 桌面上点击箭头
- 系统尝试把显式广播投递给 `com.buct.course.widget.ScheduleWidget`
- 找不到已注册的 receiver，广播被静默丢弃
- `onReceive()` 根本不执行
- `current_week` 不变化，标题和列表都不刷新

这不是“翻页逻辑失效”，而是“点击事件没有送达”。

### 当前 1.0.9.16

同一问题仍然存在：

- `ScheduleWidget.kt` 的箭头目标：新包名类
- `ScheduleDayWidget.kt` 的箭头目标：新包名类
- Manifest 实际注册：旧包名兼容壳

因此周课表和今日课表的左右箭头都受影响；标题点击、列表点击、刷新广播不受影响，因为：

- 标题点击是 `PendingIntent.getActivity`，目标 Activity 已注册
- 列表点击是 Activity PendingIntent
- 刷新广播走 `WidgetProviders.refreshAll()`，会明确发到旧包名兼容壳

## 五、根因结论

**根因：`PendingIntent.getBroadcast` 的显式组件指向未在 AndroidManifest 注册的 `com.buct.course.widget.ScheduleWidget` / `ScheduleDayWidget`，系统丢弃广播，`onReceive` 不执行。**

证据链：

1. `AndroidManifest.xml` 只有两个 widget receiver，name 都是 `com.tyust.course.widget.*`
2. `ScheduleWidget.updateAppWidget()` 的箭头 Intent 是 `Intent(context, ScheduleWidget::class.java)`，当前类在 `com.buct.course.widget`
3. `ScheduleDayWidget.buildViews()` 的 `pending()` 同样是 `Intent(context, ScheduleDayWidget::class.java)`
4. 1.0.9.13 时类在 `com.tyust.course.widget`，Manifest 也是这个类，所以同一行代码当时有效
5. 1.0.9.15 只改了包名和 Manifest 兼容壳，没有同步改 PendingIntent 目标

补充：`WidgetProviders.refreshAll()` 会向新类发广播，但新类未注册，所以只有旧壳收到；这不影响刷新，但说明“新旧双组件”只在刷新路径做了兼容，箭头路径没有。

## 六、修复方案

### 方案 A（推荐）：按实例真实 provider 生成 PendingIntent

不要硬编码新类或旧类，而是从 `AppWidgetManager` 查当前实例实际属于哪个 provider：

```kotlin
private fun providerOf(
    context: Context,
    manager: AppWidgetManager,
    appWidgetId: Int,
    isDay: Boolean
): ComponentName? {
    manager.getAppWidgetInfo(appWidgetId)?.provider?.let { return it }
    val components = if (isDay) WidgetProviders.day(context) else WidgetProviders.week(context)
    return components.firstOrNull { id ->
        manager.getAppWidgetIds(it).contains(appWidgetId)
    }
}
```

周组件 `updateAppWidget()` 中：

```kotlin
val manager = AppWidgetManager.getInstance(context)
val provider = providerOf(context, manager, appWidgetId, isDay = false)
    ?: return

val prevIntent = Intent()
    .setComponent(provider)
    .setAction(ACTION_PREV_WEEK)
val prevPendingIntent = PendingIntent.getBroadcast(
    context, 0, prevIntent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
views.setOnClickPendingIntent(R.id.widget_prev_week, prevPendingIntent)

val nextIntent = Intent()
    .setComponent(provider)
    .setAction(ACTION_NEXT_WEEK)
val nextPendingIntent = PendingIntent.getBroadcast(
    context, 1, nextIntent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
views.setOnClickPendingIntent(R.id.widget_next_week, nextPendingIntent)
```

今日课表 `buildViews()` 中：

```kotlin
val manager = AppWidgetManager.getInstance(context)
val provider = providerOf(context, manager, appWidgetId, isDay = true)
    ?: return views

fun pending(action: String, requestCode: Int): PendingIntent {
    val intent = Intent()
        .setComponent(provider)
        .setAction(action)
    return PendingIntent.getBroadcast(
        context, requestCode, intent,
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
    )
}
```

优点：

- 当前老实例 provider 是旧壳，会正确投递到旧壳，旧壳继承新逻辑，`onReceive` 正常执行
- 以后如果注册新 provider，也能自动适配
- 不需要在 Manifest 增加重复 provider，不会在小组件选择器里出现两个「课表小组件」

### 方案 B（最小热修）

把箭头目标直接改成旧包名兼容壳：

```kotlin
Intent(context, com.tyust.course.widget.ScheduleWidget::class.java)
```

今日课表同理：

```kotlin
Intent(context, com.tyust.course.widget.ScheduleDayWidget::class.java)
```

优点：一行改动，立刻恢复。
缺点：硬编码旧壳；如果以后真的启用新 provider，又会失效。只建议作为临时包。

### 方案 C（不推荐）：Manifest 再注册新 provider

在 Manifest 增加：

```xml
<receiver android:name="com.buct.course.widget.ScheduleWidget" ...>
```

问题：

- 小组件选择器会出现两个同名「课表小组件」
- 旧实例仍绑旧壳，新实例可能绑新类，行为分叉
- 解决了一个广播问题，引入选择器重复和实例类型分裂

### 附带加固

`ScheduleWidget.onReceive()` 目前用：

```kotlin
val ids = appWidgetManager.getAppWidgetIds(intent.component)
```

建议改成：

```kotlin
val ids = WidgetProviders.weekIds(context, appWidgetManager)
```

理由：

- 兼容新旧 provider 混用
- 周数本来就是全局 `current_week`，所有周组件应一起刷新
- 避免 `intent.component` 为空或只覆盖其中一套组件

今日课表已经是 `WidgetProviders.dayIds()`，无需改。

### 同源广播路径（建议一并修）

调查中发现，不止箭头使用“直接指向新类”的写法：

- `ui/screen/WidgetFontScaleDialog.kt`：字号调整后向 `com.buct.course.widget.ScheduleWidget` 和 `ScheduleDayWidget` 发 `REFRESH_WIDGET`。新类未注册，实际收不到；字号可能不会立即生效。
- `ui/screen/WidgetTitleDialog.kt`：全局标题修改后同样向新类发广播。新类未注册，可能不会立即刷新。
- `manager/AppearanceSettingsManager.kt`：`updateThemeMode()` 里创建了 `refreshIntent`，但没有 `sendBroadcast`；主题切换后的刷新路径本身没有走完。

建议把这些调用统一改成：

```kotlin
WidgetProviders.refreshAll(context)
```

或者按周/日分别用 `WidgetProviders.week(context)` / `day(context)` 逐个发。这样所有刷新路径都只依赖“实际注册的组件”，不会再因为新旧包名分裂而静默失败。

这不是本次左右箭头失效的直接根因，但属于同一次包名迁移留下的同类风险，建议在修复箭头时一并处理。

如果担心升级后桌面上仍残留 1.0.9.14 的旧 PendingIntent（旧 action `com.tyust.course.widget.PREV_WEEK`），可以在 `onReceive()` 增加旧 action 别名判断：

```kotlin
const val LEGACY_ACTION_PREV_WEEK = "com.tyust.course.widget.PREV_WEEK"
const val LEGACY_ACTION_NEXT_WEEK = "com.tyust.course.widget.NEXT_WEEK"
```

这样即使 launcher 还没重建 RemoteViews，旧点击也能落到兼容逻辑。不是必需，但可以作为升级期兜底。

## 九、结论

- 1.0.9.13 的左右箭头是正常的，因为类名和 Manifest provider 一致。
- 1.0.9.15 包名迁移后，箭头 PendingIntent 指到未注册的新类，广播被系统丢弃。
- 这是 1.0.9.15 引入的回归，1.0.9.16 仍在。
- 推荐方案 A：按实例真实 provider 生成 PendingIntent，同时把周组件的 `onReceive` 改为 `WidgetProviders.weekIds`。
- 改完后周课表和今日课表的左右箭头都应恢复；不需要在 Manifest 增加重复 provider。

## 十、本次实际修复与真机验证

### 实际改动

1. `widget/WidgetProviders.kt`

3. `widget/ScheduleDayWidget.kt`
   - 左/右箭头和「回到今天」改为 `Intent().setComponent(widgetProvider)`。
   - 增加旧 action `com.tyust.course.widget.DAY_PREV/NEXT/TODAY` 兼容。
   - 刷新分支改用 `ScheduleWidget.ACTION_REFRESH`。
