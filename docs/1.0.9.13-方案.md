## 1. 「更新 Cookie」遇到二次验证直接失败

### 现状（根因）
- 设置页「更新 Cookie」→ `SettingsRoute.refreshCookieManually()` → `SessionRenewer.request(manual=true)`，用**保存的密码静默再登录一次**。
- `SessionRenewer` 里给网关实现的回调只有 4 个：`onSuccess` / `onCaptchaRequired` / `onCaptchaInvalid` / `onInvalidCredentials` / `onError`。
- 而 `PasswordLoginCallback` 里真正表示二次验证的是 **`onSecondaryVerificationRequired(phoneMasked)`**、`onSecondarySmsSent(expire)`、`onSecondarySmsInvalid(msg)`——`SessionRenewer` **没有实现**，走了接口默认实现：
  ```kotlin
  fun onSecondaryVerificationRequired(phoneMasked: String) =
      onError("登录需要短信二次验证，请使用密码登录页完成验证")
  ```
  → 被归类成 `RecoveryFailure.Network` → 弹「暂时无法连接，请稍后重试」（你截图里那个 toast）。
- 也就是说：**风控要求二次验证时，续期通道把验证请求当成了网络错误**，所以永远不弹验证码。

### 方案
1. `SessionRenewer` 保留「待验证会话」：网关实例不销毁，新增状态
   `Verifying(phoneMasked, captchaBytes)`，对外暴露 `submitCaptcha()` / `submitSmsCode()` / `refreshCaptcha()`。
2. 补齐回调：
   - `onSecondaryVerificationRequired` → 进入 `Verifying`，拉一张图形码，回调 UI 弹窗；
   - `onSecondarySmsSent` → 开始倒计时；
   - `onSecondarySmsInvalid` → 弹窗内提示「验证码错误/过期」，允许重发。
3. 弹窗：把 `LoginScreen` 里现有的 `SecondarySmsVerificationDialog`（图形码 + 短信码 + 内联发送/倒计时）抽成公共组件，设置页直接复用，交互与登录页完全一致。
4. 失败提示细分：
   - 网络 → 「暂时无法连接」；
   - 密码被改 → 「密码已变更，请重新登录」；
   - 验证超时/取消 → 回到可再次点「更新 Cookie」的状态。
5. 安全：切换账号、退出设置页、进程回收时 `gateway.clearSensitiveState()`，不把验证码/密码留在内存。

### 改动文件
`utils/SessionRenewer.kt`、`utils/SessionRecovery*.kt`、`ui/route/SettingsRoute.kt`、`ui/screen/LoginScreen.kt`（抽弹窗）、`login/BuctSsoLoginManager.kt`（暴露图形码刷新与二次验证状态）。

### 验收
设置页点「更新 Cookie」→ 触发风控时弹出与登录页一致的验证弹窗 → 输图形码 → 收短信 → 输短信码 → 提示「登录状态已更新」，且成绩/课表不再提示需要登录。

## 3. 显示 901 时就地更新 Cookie

### 现状
- `EmptyClassroomApi` 在教务返回异常时抛 `IOException("HTTP ${code}")`，`EmptyClassroomDialog` 把 `e.message` 原样显示——就是你看到的「901」。
- 只能自己退出去设置页点「更新 Cookie」。

### 方案
1. `EmptyClassroomApi`：把 901 / 401 / 未登录页 统一抛成 `SessionExpiredException`（保留原始 code）。
2. 错误态 UI：识别会话失效 → 显示
   `登录状态已失效（901）` + 一个 **「更新登录状态」** 按钮。
3. 点按钮 → 就地走第 1 项的续期流程（含二次验证弹窗）→ 成功后**自动重试当前查询**，失败保留按钮。
4. 抽成通用组件 `SessionExpiredHint`，后续成绩页/课表页遇到同类错误可复用。

### 改动文件
`network/EmptyClassroomApi.kt`、`ui/screen/EmptyClassroomDialog.kt`、新增 `ui/system/SessionExpiredHint.kt`。

## 4. 快速切换他人课表 + 小组件选账号

### 现状
- 多账号能力已有：`UserManager.savedAccounts` + `switchToAccount(key)`，但入口藏在「设置 → 账号管理」，要三步。
- 课表缓存本身按账号隔离（`schedule_${account}_${school}_${term}`），具备「读任意账号缓存」的基础。
- 小组件固定读**当前账号**的缓存。

### 方案
**A. 快速切换（App 内）**
- 课表页顶部标题区加一个账号芯片（头像圆点 + 名字），点击弹出底部面板：
  - 列出已保存账号（姓名、学号后四位、是否当前）；
  - 点选即 `switchToAccount` 并刷新课表/成绩/考试；
  - 面板底部「管理账号」跳设置页。
- 切换时复用现有 `requests.cancel(...)` 机制，避免旧账号请求回写新账号界面。

**B. 小组件按实例选账号（每个小组件各自指定）**
- 每个 appWidgetId 独立存配置：`widget_account_<id>`（账号）、`widget_title_<id>`（可选名字）。
- **添加小组件时弹出配置页**（`WidgetConfigActivity`，manifest 里声明 `android.appwidget.configure`）：选账号 + 可改名字，确认后写入该实例。
- **已添加的小组件**：点小组件标题区域 → 打开同一个配置页修改（PendingIntent 带 appWidgetId），比“去设置里找一个不知道是哪一个的列表”直观。
- 小组件按自己配置的 storageKey 读 `schedule_cache`；未配置时跟随当前账号；该账号无缓存时显示「该账号暂无课表缓存」。
- 改完立即只刷新该实例（不再全量广播）。

### 改动文件
`ui/screen/ScheduleScreen.kt`（顶栏芯片）、新增 `ui/screen/AccountSwitcherSheet.kt`、`ui/route/ScheduleRoute.kt`、`manager/ScheduleSettingsManager.kt`、`widget/ScheduleDayWidgetService.kt`、`widget/ScheduleWidgetService.kt`、`ui/screen/ScheduleSettingsScreen.kt`。

### 取舍
- 先做「直接切换登录态」，不做「只读预览另一个账号」——后者要再造一套只读上下文，收益有限。
- 小组件配置按实例存（`appWidgetId`），不同实例可以分别显示不同账号、不同标题。

## 5. App 内匿名反馈（双向会话，后台像 QQ 一样按人折叠）

### 需求
- 设置页可直接发消息，**不需要登录**；
- 后台按「匿名设备」聚合成一个个会话（列表折叠，点进去看全文）；
- 我可以回复，**同学在 App 里能看到我的回复**；
- 不限条数；
- 明确告知：后台看到的是随机匿名安装 ID，不含姓名/学号/账号。

### 关键约束（先说结论）
你这台服务器：**1.6GB 内存 / 2 vCPU / 40GB 盘（已用 3.2G）/ 没装 Docker**，当前可用约 1.1GB。
另外：App 面向国内 Android，**没有 GMS 推送**，任何方案在 App 关掉时都收不到实时消息，只能靠下次打开时拉取。

### 两条路线对比（实测/查证后的数字）

| | **A. Tinode（现成 IM）** | **B. 轻量自建（复用现有 Python+SQLite）** |
|---|---|---|
| 服务端 | PostgreSQL + Tinode（Go）+ 可选 Tinode Web | 在 `beihua-stats` 里加表与接口，**零新增进程** |
| 内存占用 | 约 +250MB（PG 调小 shared_buffers + Tinode） | 约 +10MB |
| 部署 | 无 Docker → 装 Docker 或原生 PG+二进制；nginx 加 wss 反代；init-db；管理员账号 | 改 `server.py` + 重启 systemd，10 分钟 |
| 匿名身份 | 支持 anonymous 用户，按设备派生账号（正好贴合） | installId 直接当会话 ID |
| App 端 | `co.tinode:tinode-sdk`（jackson/websocket/icu4j，约 +3MB）**只给协议层**，聊天 UI 仍要自己写两个页面 | 一个会话页（气泡 + 输入框 + 轮询），约 300 行 |
| 后台 | Tinode Web（React）登录管理员，会话天然是列表 | 现成 `/stats?token=` 旁边加 `/feedback` 页面，左列表右对话 |
| 实时性 | App 前台可 WebSocket 实时；后台无 GMS 推送，关掉后同样收不到 | 打开会话时 5 秒轮询，效果接近 |
| 许可/维护 | 服务端 GPL-3.0、Beta 质量；两套服务升级 + PG 备份 | 自己的代码，备份就是现有 `stats.db` |
| 结论 | 功能强，但**为一个反馈通道引入一整套 IM 基础设施**，小机器上性价比低 | 满足全部需求，成本最低，后续可平滑升级 |

**建议走 B**：需求本质是「留言 + 回复」，不是社交 IM；B 的体验差别主要在“实时性”，而国内无 GMS 时 A 也拿不到推送，这个优势不成立。若以后反馈量很大、想要附件/已读回执/多客服，再迁 Tinode（数据模型能对上：一个 installId = 一个会话）。

### B 的具体设计

**数据表（沿用 `stats.db`）**
```sql
CREATE TABLE IF NOT EXISTS feedback_messages(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  install_id TEXT NOT NULL,
  sender TEXT NOT NULL,          -- 'user' | 'admin'
  body TEXT NOT NULL,
  version TEXT, platform TEXT,
  created_at TEXT NOT NULL,
  read_by_user INTEGER DEFAULT 0,
  read_by_admin INTEGER DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_feedback_thread ON feedback_messages(install_id, id);
```

**接口**
| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/feedback/send` | App 发送，`install_id + body`（10–1000 字），不限条数 |
| GET | `/api/feedback/thread?install_id=…&since_id=…` | App 拉取会话（含我的回复），返回未读数 |
| GET | `/feedback?token=…` | 后台会话列表（按最后消息倒序，显示匿名 ID + 末条摘要 + 未读红点） |
| GET | `/feedback/thread?token=…&install_id=…` | 后台打开某个会话，看全文（含版本号/设备） |
| POST | `/feedback/reply` | 后台回复（带 token），写 `sender='admin'` |

**后台页面（像 QQ 的两栏）**
- 左：会话列表，每条 = 匿名 ID（前 8 位）+ 最后一条消息 + 时间 + 未读红点；点开右栏；
- 右：气泡对话（用户灰、我蓝）、输入框直接回车发送；
- 顶部显示该 installId 的版本、最后活跃时间（关联 `installs` 表），**没有任何实名信息**；
- 所有正文 HTML 转义。

**App 端**
- 设置 →「帮助与反馈」→ 意见反馈（**独立页面，不是一次性弹窗**）：
  - 顶部固定说明条：「你正在以匿名身份反馈，我们只会看到设备随机 ID `a1b2…`，不包含姓名、学号、密码」；
  - 气泡列表（我的/官方）、底部输入框、发送；
  - 打开时立即拉取 + 每 5 秒轮询；离开页面停止；
  - 我在后台回复后，同学下次打开能看到；设置页「意见反馈」行显示红点（进入 App / 打开设置时轻量拉一次未读数）。
- 重装 App 会生成新 installId，历史会话不跟随（这一点会写在说明文案里）。

### 改动文件
- App：新增 `ui/screen/FeedbackScreen.kt`、`network/FeedbackApi.kt`、`analytics/InstallId.kt`（从 `UsageStatsReporter` 抽出）；`ui/screen/SettingsScreen.kt`、`ui/route/SettingsRoute.kt` 加入口与红点。
- 服务端：`server/usage-stats/server.py` 加表、5 个路由、两栏后台页；**改完重启 `beihua-stats`，部署等你点头**。

### 验收
- 未登录/新装能发消息；
- 后台看到按匿名 ID 折叠的会话，点进去能看全文并回复；
- App 重新打开能看到回复，设置页有红点；
- 说明文案明确写出「只收到匿名设备 ID」。

## 6. 匿名社交与课表分享（分期，先定架构）

> 这一段是把「反馈」延伸成「匿名用户之间互加、聊天、互传课表」。本质是**校园 UGC 社交**，不是加一个按钮，必须分期做，并且先定身份与治理规则。

### 6.1 身份体系
| 字段 | 说明 |
|---|---|
| `install_id` | 设备随机 ID（现有），账号唯一依据；重装/换机会变成新账号 |
| `display_id` | 对外**唯一短号**（如 `BH-7F3K2Q`），用于加好友，不可修改 |
| `nickname` | 默认**随机昵称**（如「晚风」「薄荷汽水」），2–12 字，可改，**不唯一** |
| `avatar_color` | 由 uid 派生，无需上传头像 |
| `role` | `user` / `admin` |

- 管理员账号固定为 **「柳岸」**（display_id 如 `BH-ADMIN`），**全员默认联系人**，就是现在这条反馈通道的升级版。
- 设置页展示「我的短号 + 昵称」，可复制短号；换机丢会话要在文案里说明。

### 6.2 加好友：只认短号，不建议按昵称搜
- 昵称**可重复、可冒充**，一旦开放昵称搜索，骚扰和冒充成本几乎为零。
- 方案：搜索 **display_id**（唯一）→ 显示昵称/头像色 → 直接建立会话（无好友申请）。
- 对方可**拉黑/举报**；被拉黑后消息发不出且有提示。
- 线下交换短号最自然（截图/报号），不需要通讯录权限。

### 6.3 消息规则
- 1:1 文本（≤1000 字）+ 课表文件（≤200KB）。
- 打开会话 3–5 秒轮询，未读红点，本地保留最近 50 条。
- **必须限流**：每人每分钟 20 条、每天 200 条。陌生人社交放开无限发送＝一条脚本就能刷爆你和同学的手机（反馈通道可以无限，因为只发给你一个人）。
- 举报：长按消息 → 举报 / 拉黑；后台能看到被举报会话的原文（治理必需，否则无法处理骚扰）。

### 6.4 课表分享
- 现状：只有 `.ics` 导出（给系统日历），**没有可回传的课表文件**。
- 新增格式：`{type:"beihua.schedule", v:1, nickname, term, exportedAt, courses:[...]}`（复用现有课程 JSON）。
- 聊天里发文件 → 对方点开预览（几门课、哪个学期）→ 导入为「朋友的课表」。
- 本地存 `shared_schedules/<uid>.json`，最多 10 份，设置里可删除。
- 首次分享弹隐私提示：课表含上课时间/教室/教师。

### 6.5 小组件来源
- 每个小组件实例可选：**当前账号 / 已保存账号 / 朋友的课表（昵称）**。
- 存在 `widget_source_<appWidgetId>`；无数据时显示「该来源暂无课表」。
- 与第 4 项的小组件实例配置合并成同一个配置页（来源 + 名字）。

### 6.6 架构：Tinode 还是自建？
| | A. Tinode | B. 自建（复用 stats 服务） |
|---|---|---|
| IM 内核 | 现成（联系人/搜索/消息/文件/已读） | 4 张表 + 约 8 个接口 |
| 服务端成本 | PostgreSQL + Tinode，约 +250MB，两套服务 | 0 新增进程，约 +10MB |
| App 端 | **仍要自己写聊天 UI**（SDK 只是协议层） | 同样自己写 UI |
| 后台 | Tinode Web（现成，但多一套账号体系） | 现有 token 后台加一页 |
| 无 GMS 推送 | 关掉 App 一样收不到 | 同样收不到 |
| 工期 | 4–6 天（部署+SDK+UI+联调） | 2–3 天 |
| 结论 | 功能全但重 | **推荐**：规模匹配、运维简单 |

### 6.6.1 可选的开源复用清单（2026-11 查证）

| 项目 | 形态 | 数据库/内存 | 自带界面 | 许可/成熟度 | 对我们的适配度 |
|---|---|---|---|---|---|
| **ClickClack** | 单个 Go 二进制，内置 Svelte 网页 | SQLite（WAL/FTS5），约 60MB | ✅ 有频道/私聊/文件/实时 | MIT，**184★、V1 开发中（2026-05 建仓）** | 部署最简单；但英文界面、工作区模型、无匿名身份，Android 端仍要自己写客户端 |
| **PocketBase** | 单二进制后端套件 | SQLite，约 50MB | ⚠️ 只有数据库后台 | MIT，4 万★，成熟 | 免写 CRUD/文件/实时；但没有聊天界面，匿名登录要写 Go 钩子 |
| **Tinode** | Go 服务 + PG/MySQL | 需 PG，约 +250MB | ✅ Web/Android 官方客户端 | GPL-3.0，1.3 万★，Beta | 功能最全；服务重、SDK 只给协议层 |
| **Prosody (XMPP)** | 轻量 XMPP 服务 | SQLite，约 40MB | ⚠️ 用第三方客户端 | MIT，极成熟 | 协议稳但注册/审核/中文体验差，App 要引 Smack |
| **Chatwoot** | Rails + PG + Redis | **≥2GB** | ✅ 客服收件箱最好看 | MIT/部分商业 | 内存不够，直接排除 |

**判断**：
- **9.13 仍走自建**——需求只是「反馈会话」，加一个服务不值当。
- 如果 9.14 要做**真聊天**（好友+文件+实时），优先评估 **ClickClack**：单二进制、SQLite、自带界面，运维成本和现在一样；代价是它很年轻（184★、V1）、英文 UI、匿名身份要改造（把 installId 映射成它的 guest/bot 账号）。
- **PocketBase** 作为备选：成熟稳定，但没有聊天界面，省的是后端不是前端。
- 结论：**先自建落地 9.13，9.14 前用一版真实反馈量评估要不要换 ClickClack**；换的话数据可以迁移（installId → 用户，消息表结构一一对应）。

> 结论：仍建议 **B 自建**，但**按下面三期走**，不要一次上线社交。

### 6.7 必须配套的治理（否则别上线）
1. 举报 + 拉黑 + 后台封禁（按 install_id / 短号）；
2. **服务器端总开关**：可一键关闭「陌生人聊天」，只保留反馈通道；
3. 文件限额（200KB / 每人每天 10 个）；
4. 首次使用弹一次「匿名 ≠ 无责任」提示 + 简单用户约定；
5. 不做群聊、图片、语音（先控制复杂度与审核成本）。
> 提醒：一旦上线陌生人消息，你就成了 UGC 运营者，需要对骚扰/违规内容有处置能力，这部分工作量要算进去。

### 6.8 分期
