## 四、密码登录协议（完全可用，iOS 直接照抄）

### 4.1 端点

| 项 | 值 |
|---|---|
| 登录域 | `https://sidportal.buct.edu.cn` |
| 登录页 | `GET /login?service=<service>` |
| 登录提交 | `POST /login?service=<service>&state=<random>&client_id=<admin-client b64>` |
| 教务跳转 | `https://jwglxt.buct.edu.cn/sso/jziotlogin` |
| 图形验证码 | `GET /api/captcha/generate/DEFAULT` |

### 4.2 第一步：GET 登录页，提取两个字段

```
GET /login?service=<service>
```
从返回 HTML 提取（`<p id="...">` 元素）：
- `login-page-flowkey` → 提交用 `execution`（格式 `UUID_JWT`，形如 `277a96ce-...-4b55ecbd6d75_ZXlKaGJHY2lPaUp...`）
- `login-croypto` → AES 密钥（Base64 字符串，形如 `fsKdt8Vpq8BtvoaKi2/5aw==`）

### 4.3 第二步：加密密码

```kotlin
// CryptoJS.AES.encrypt(明文, key=Base64.parse(croypto), {mode:ECB, padding:Pkcs7}).toString()
// = AES-ECB + PKCS7 填充，key = Base64 解码 croypto，输出 Base64
password = AES_ECB_PKCS5(b64decode(croypto), 明文密码)  // PKCS5/PKCS7 在 16 字节块下等价
```

### 4.4 第三步：POST 表单（application/x-www-form-urlencoded）

```
type=UsernamePassword
_eventId=submit
username=<学号>
password=<AES密文>
croypto=<login-croypto>
execution=<login-page-flowkey>
captcha_code=<图形码，无则空>
captcha_payload=AES_ECB_PKCS5(b64decode(croypto), "{}")   ← 重要：内容就是 "{}"
geolocation=
```

请求头需带：`User-Agent`（Chrome 154 UA）、`Referer`（当前 login URL）、`Origin: https://sidportal.buct.edu.cn`（浏览器有，原生可不带）。

### 4.5 第四步：302 跟随链

- 成功 → `302 Location: https://sidportal.buct.edu.cn/oauth2.0/callbackAuthorize?client_id=...&ticket=ST-...`（教务 service）或 `.../login?service=...&ticket=ST-...`
- 用 CookieJar **自动跟随**（OkHttp `followRedirects` / iOS URLSession 自动跟随，cookie 按域种下）
- 教务最终：`jwglxt.buct.edu.cn` 会话建立

### 4.6 表单字段与浏览器 cURL 实测对照

浏览器抓到的真实登录 POST（`decrypt_browser_login.js` 已解密验证 App 与浏览器完全一致）：

```
username=2024xxxxxx&type=UsernamePassword&_eventId=submit&geolocation=&
execution=<UUID_JWT>&captcha_code=&croypto=<key>&password=<AES>&captcha_payload=<AES("{}")>
```

## 五、短信登录协议（完全可用）

金智短信登录是**独立三接口链**（不走 CAS 表单）：

| 步骤 | 请求 | 说明 |
|---|---|---|
| 1 | `POST /sso-extend/protected/api/aggregate/sms/publicNoToken/generate`<br>body `{"phone":"<学号>","type":"DEFAULT"}` | 返回图形验证码 PNG；需 `Csrf-Key` / `Csrf-Value` / `Device-Id` 三个头 |
| 2 | `GET /sso-extend/protected/api/aggregate/sms/publicNoToken/sendCheckCaptcha/DEFAULT/<图形码>/<学号>/0008` | 校验图形码并触发短信。**业务号必须 `0008`**（0024 能发短信但校验查不到记录）；返回 `{"result":true}` |
| 3 | `POST /api/protected/sms/checkTokenResult`<br>body `{username, code:<短信码>, deviceId, ...}` | 校验短信码；成功即完成登录 |

关键约束：
- **CSRF 算法**：`Csrf-Key` / `Csrf-Value` 由金智前端 JS（`buct_deploy.js`）算法生成（脚本已留档），App 内已复刻（`BuctSmsLoginManager.kt` 的 `csrfKey()`/`csrfValue()`）。
- **Device-Id**：三步必须用**同一个**设备指纹，否则 `checkTokenResult` 恒返回错误码 `1320009`。
- 实现细节直接读 `BuctSmsLoginManager.kt` 顶部注释 + 源码。

## 六、通行密钥：注册 400 卡点完整排查史（重要！）

### 6.1 现状

- 未注册设备：App 内输密码 → 自动走 `POST /webauthn/register` → **恒定 `400 {"messages":["operation not allowed"]}`**。
- 已注册设备：`POST /webauthn/authenticate`（JSON 挑战）→ Credential Manager 断言 → `POST {finish}` → 登录，**这条链 App 已实现**（`BuctWebAuthnManager.kt`）。

### 6.2 register 请求形态（App 当前实现）

```
POST https://sidportal.buct.edu.cn/webauthn/register
Headers: X-CSRF-TOKEN: csrfToken   Content-Type: application/x-www-form-urlencoded;charset=UTF-8
Body:    username=2024xxxxxx&displayName=test&credentialNickname=test&requireResidentKey=false&sessionToken=null
```

### 6.3 已逐一证伪的假设（**不要重复尝试**）

| # | 假设 | 结论 |
|---|---|---|
| 1 | 限 1 个凭据（删掉电脑凭据） | ✗ 仍 400 |
| 2 | 缺 `_zte_cid_/_zte_sid_` cookie | ✗ 附加无效 |
| 3 | 缺 `tfstk/_ga/sidTheme` 等 cookie | ✗ 附加无效 |
| 4 | `X-CSRF-TOKEN` 需真实值（非字面量 csrfToken） | ✗ 随机/无/字面量均 400（探针 6 形态全 400/405） |
| 5 | `Referer`/`User-Agent` 变体 | ✗ 无关 |
| 6 | 需先访问 safe-center 建立上下文 | ✗ 已访问仍 400 |
| 7 | `?skipCustom=true` 会话 | ✗ 仍 400 |
| 8 | 登录入口不对（教务 service vs 管理 admin-client service） | ✗ 已复刻 admin-client 完整 OAuth2 授权链（service+state+client_id，302→ticket→authorize→code→sidself 会话 200），仍 400 |
| 9 | `captcha_payload`/`execution` 内容差异 | ✗ 已解密：浏览器与 App 同为 `AES(croypto,"{}")`、execution 同 UUID_JWT 格式 |
| 10 | **cookie 混发 sidself 域 TGC**（`SOURCEID_TGC`/`rg_objectid` 误按全局域发给 sidportal） | ✗ 2026-10-17 已修复（register 请求 cookie 已干净），**仍 400** |
| 11 | **"浏览器会话有权限、App 没有"** | ✗ **关键证伪**：浏览器 Cors fetch 实测 `net::ERR_FAILED 400`；此前 `no-cors` 模式显示的 "2xx" 是 **opaque 响应状态误读**，浏览器 register 实际也 400 |
| 12 | 静态 JS 逆向找前置接口 | ✗ 已下载全部 138 个 chunk + 主 bundle + vendor + scripts 扫描，**register 调用代码不在任何静态 JS 中**（URL 动态拼接或由前置接口签发） |

### 6.4 当前唯一未排除的方向（最后线索）

1. **浏览器真实点击"创建通行密钥"的请求序列从未抓到**——之前 Network 里的 register 请求全是开发者手工 fetch 产生的，不是真实点击。真实点击在 register **之前**大概率有一个或多个前置请求（取挑战值/建注册会话/签发 sessionToken）。
2. 安全设置页加载时 Console 多次出现 **`{code: 412, message: 'Precondition Failed'}`**（某个前置接口 412），怀疑与 register 权限相关——该 412 接口 URL 未定位。
3. **建议的下一步（iOS 同学接手后第一件事）**：
   - 在已登录浏览器安全设置页，F12 Network 勾"保留日志"，**真实鼠标点击「通行密钥」区域的「创建」按钮**；
   - 截取 register 请求**前面出现的全部请求**（URL + 状态码 + 请求头 + Cookie）；
   - 重点找：`/webauthn/*` 前置、`sessionToken` 签发、`412` 接口、以及真实 register 的完整 `Cookie`（与 App 对比差什么）。

### 6.5 其他已知细节

- `client_id`：`OC4wNS4wNS4wNy4wMC4wMy4wMS4wMS4w`（= `admin-client` 的 base64）
- PASSKEY_AUTH_SERVICE：
  `https://sidportal.buct.edu.cn/oauth2.0/callbackAuthorize?client_id=OC4wNS4wNS4wNy4wMC4wMy4wMS4wMS4w&redirect_uri=https%3A%2F%2Fsidself.buct.edu.cn%2Flogin%2Foauth2%2Fcode%2Fadmin-client&response_type=code&client_name=CasOAuthClient`
- 登录 URL 顶层需随 `service` 一并带 `state`（随机，SecureRandom 32B base64url）+ `client_id`
- register/authenticate 的 finish 提交：`{HOST}/{finish 相对路径}`，body 含 `requestId` + `credential`(断言 JSON) + `sessionToken:null`
